楽天RPP 20円広告 暴走抑制・動的予算ナビゲーション
Claude開発仕様書 v3

Phase 1：ショップ全体の予算制御に集中／商品単位制御は実装しない

## 1. 最重要目的

本ツールの対象は、楽天RPPの「全体CPC上限20円広告」である。KW広告やRPP全体ROASを主目的指標にしない。

20円広告ROASは400%以上を理想とし、暴走傾向を早期検知した場合でも300%以上への着地を防衛目標とする。

目的は単純な広告費削減ではない。売上機会をできるだけ残しつつ、異常配信時の無駄打ちを予算投入タイミングと投入額で抑制する。

## 2. 楽天RPPの制約・用語

「全体20円」はCPC20円固定ではなく、クリック単価の上限が20円。平均CPCが20円未満になるのは正常であり、それだけで異常判定しない。

当日の広告ROAS/CVR/広告売上は確認できない。最新の成果データは前日分まで。

当日は累計クリック数、累計実績額、現在の設定予算、予算上限到達の有無を使用する。平均CPCは実績額÷クリック数で自動算出する。

KW広告を出すには全体20円広告への参加が必要。Phase 1では商品単位の広告削除・復活機能は作らない。

KW ROAS、RPP全体ROASは参考表示可。ただし「20円ROAS」と必ず明記し、混同させない。

## 3. Phase 1の基本思想

ショップ全体の20円広告を、朝の前日確定データと当日3回の観測で逐次制御する。

朝に1日分の投入額を固定しない。「開始予算→9:30再判定→15:00再判定→18:30再判定」という逐次判断型ナビゲーションとする。

暴走警戒時は予算切れを失敗と扱わず、「意図的停止」として18:30まで停止継続を推奨してよい。

ツールは提案のみ行い、最終実行は人間。提案内容と実際の行動を両方保存する。

## 4. 日タイプと推奨日予算上限

日タイプはカレンダーから判定する。5の倍数は自動判定し、マラソン／スーパーSALE等は管理画面から開始日時・終了日時を翌月分まで手入力可能にする。開始・終了時刻を保持する。

初期の推奨上限は下表。絶対上限ではない。好調と判断した場合、ツールは理由付きで超過提案してよい。

| 日タイプ | 初期推奨上限 |
|---|---|
| 通常日 | 70,000円 |
| 5の倍数 | 90,000円 |
| セールのみ | 90,000円 |
| セール＋5の倍数 | 120,000円 |
| セール最終日 | 70,000円（他条件より優先） |

## 6. 朝の前日確定データによる初期警戒基準 v1

5〜8月データを用いた事前バックテストから得た初期ルールとして、次を設定値として実装する。永久固定ではなく、設定変更・再バックテスト可能にする。

「前日の20円実績額 >= 30,000円」または「前日の20円ROAS < 225%」なら、翌日を強警戒で開始する。

それ以外は通常開始とする。ただし前日正常でも突発暴走は発生するため、9:30チェックを省略しない。

過去検証の目安：翌日20円ROAS<300%の捕捉 約82%、<200% 約91%、<100% 約90%。これらは5〜8月の初期検証値であり、ツール内で再計算できるようにする。

朝の開始予算も5,000円単位でツールが提案する。開始予算の具体的閾値は固定せず、過去データと今後の観測データから調整可能にする。

## 7. 当日の標準観測

標準観測時刻は9:30、15:00、18:30。実際の確認時刻は自動保存する。

入力項目：累計クリック数／累計実績額／現在の設定予算／予算上限到達の有無。平均CPCは自動計算。

時刻枠の初期許容範囲：9:00〜10:00、14:30〜15:30、18:00〜19:00。実時刻も保持する。

欠損は0にしない。「未観測」とする。休日の予定された未観測と、記録忘れによる未観測を区別する。欠損した時間帯だけ比較母数から除外し、他のデータは利用する。

## 8. 9:30／15:00／18:30の役割

9:30：朝の初動を確認。開始予算を維持するか、5,000円単位で追加するか、追加せず予算切れを許容するかを判断。

15:00：最重要の中間判定。9:30→15:00の実績額増加・クリック増加・相対CPCを評価し、「追加」「維持」「18:30まで意図的停止」を判断。

18:30：夜間需要に向けた最終投入。残りの推奨上限、店舗全体の注文時間帯傾向、当日の消化状態から5,000円単位で追加額を提案。好調なら推奨上限超過も理由付きで提案可能。

各時刻の判断は、その時点までに取得できたデータだけを使う。未来のROAS/CVRを使用しない。

## 9. 当日判定ロジックの作り方

当日の固定閾値は現時点で人為的に決めすぎない。RPP.xlsx等の時間別履歴を蓄積し、同じ時刻枠・同じ日タイプの過去中央値と比較する。

主指標：実績額進捗倍率、クリック進捗倍率。補助指標：平均CPCの通常比。CPC単独では警告しない。

比較対象が少ない場合は「同一複合条件→同一セール種別→販促日全般→同時刻全体」の順で条件を緩め、判定信頼度を下げる。

初期版は説明可能なルールベースとし、ブラックボックス機械学習を中心にしない。

## 10. 予算提案の出力形式

各判定で必ず具体的な行動を1つ提示する。例：「追加しない」「5,000円追加」「15,000円追加」「18:30まで意図的停止」「設定予算を45,000円へ変更」。

表示項目：現在時刻／現在設定予算／本日の推奨上限／推奨追加額／変更後設定予算／次回確認時刻／判断理由／判定信頼度。

推奨追加額は5,000円単位に丸める。推奨上限を超える場合は「上限超過提案」と明示し、超過を勧める理由を必須表示する。

## 11. 提案と実行履歴

ツールの提案後、人間が「提案どおり実行／別金額を実行／何もしなかった」を記録できるようにする。

保存：提案時刻、提案額、提案理由、実際の変更額、変更後予算、実行時刻、任意メモ。

翌日確定した20円ROAS等と結びつけ、「どの判断・行動が20円ROAS300%以上の防衛と売上確保に寄与したか」を後から検証できる構造にする。

## 12. 前日18:30と翌朝の扱い

前日18:30には、翌日のカレンダー条件だけを使った「仮プラン」を表示可能にする。例：翌日の日タイプ、推奨上限、暫定開始予算、注意事項。

前日18:30時点では当日の最終20円ROASが未確定なので、翌日の正式な危険度を断定しない。

翌朝、前日確定RPPを取り込んだ時点で正式プランに更新し、開始予算を確定する。

## 13. 注文時間帯データ

受注日_1時間単位集計は広告・SEOを含む店舗全体の注文であり、RPPの時間別CVRではない。夜間需要の代理指標としてのみ使用する。

曜日、通常日／販促日、可能ならイベント種別ごとに時間帯構成比を算出し、18:30の夜用予算判断に利用する。

## 14. 直近4か月カレンダー

直近4か月を月カレンダー表示する。主表示は20円ROAS。

20円ROAS <100%：赤、100〜300%：橙、>300%：緑。

各セル：ROAS / 20=20円実績 / KW=KW実績 / 計=実績額 / 比率=計がその月に占める割合。

計実績額：7万円超=橙、10万円超=赤。比率：各月の上位10%=赤、上位20%=オレンジ、他=黒。

比率は各月とも1日〜最新日の同じ日付までで揃えて算出する。例：最新が8/25なら各月1〜25日。

暴走日・抑制日等の手動タグも保持できるようにする。

## 15. バックテスト機能

5〜8月の過去RPPと暴走カレンダー、イベント情報を使い、判定ルールを再検証できる画面を作る。

最低限表示：20円ROAS<300%の捕捉率、<200%の捕捉率、<100%の捕捉率、正常日の誤警報率、警戒を出した翌日に実際に悪化した割合。

閾値（例：20円実績30,000円、20円ROAS225%）をUIから変更し、結果を比較可能にする。

将来9月以降のデータを追加したら同じ方法で再検証できる。

## 16. Phase 1では実装しないもの

商品単位の一時広告削除候補

商品単位の復活候補

KWだけ残して20円だけ停止するような不可能な制御

まずショップ全体の予算制御で効果を検証し、必要性が確認された場合のみPhase 2として追加する。

## 17. データ取込と堅牢性

同梱の5〜8月RPPデータを実際に解析して列構造・文字コード・ZIP内ZIP・先頭説明行等へ対応する。実ファイルを推測で扱わない。

欠損日があっても落ちない。欠損を明示し、比較母数から除外する。

RPP当日時間別記録XLSX、注文時間帯XLSX、暴走カレンダー画像も参考資料として同梱する。将来スクリーンショットから当日値を取り込む拡張を想定し、入力層を分離しておく。

## 18. 将来のスクリーンショット自動化

将来的にはRMS当日画面を9:30／15:00／18:30に保存し、画像からクリック数・実績額・設定予算・上限到達状態を取り込む可能性がある。

Phase 1でOCR自動化を必須にしないが、手入力画面とデータ保存形式を分離し、後から画像取込モジュールを追加しやすい設計にする。

## 19. 画面構成の最低要件

A. ダッシュボード：本日の日タイプ、20円広告の危険度、本日推奨上限、開始予算、次回チェック、前日20円ROAS/実績。

B. 当日チェック：9:30/15:00/18:30入力、推奨追加額、変更後予算、理由、意図的停止。

C. イベントカレンダー：イベント名、開始日時、終了日時の登録・編集。5の倍数は自動。

D. 4か月カレンダー：指定色条件。

E. 履歴：提案と実行、翌日確定20円ROAS。

F. バックテスト／設定：基準値・日タイプ別予算上限・追加単位等。

## 20. やってはいけない実装

「ROAS」とだけ表示し、20円ROASとRPP全体ROASを混同する。

当日のROAS/CVRが見える前提で判断する。

平均CPC<20円を異常とする。

実績額が多いだけで暴走と断定する。

セール／5の倍数を通常日と同一基準で扱う。

日予算上限を絶対上限として強制する。

朝に9:30/15:00/18:30の追加額を固定してしまい、その後の実績で再計算しない。

欠損値を0として扱う。

Phase 1で商品単位広告削除を実装する。

## 21. 初期版の完成条件

1) 5〜8月RPPデータを読み込める。

2) 20円広告指標とKW指標を区別して表示できる。

3) イベント日時を登録し、5の倍数とセール最終日を判定できる。

4) 日タイプ別推奨上限を適用できる。

5) 前日確定値から通常／強警戒を判定し、開始予算を5,000円単位で提案できる。

6) 9:30/15:00/18:30の当日値を保存し、逐次予算提案できる。

7) 意図的停止を正式な推奨状態として扱える。

8) 提案と実際の行動を記録できる。

9) 直近4か月カレンダーを指定条件で表示できる。

10) バックテストで初期基準値を再検証できる。

11) 欠損・休日・記録忘れに耐える。

12) すべての提案に理由と信頼度を表示する。

## 22. Claudeへの進め方

最初に同梱ファイルを解析し、データ構造と取込方針を報告する。その後、取込→正規化→カレンダー→イベント設定→朝判定→当日チェック→提案/実行履歴→バックテストの順で実装する。

仕様と実ファイルが異なる場合は実ファイルを優先し、差異を説明する。実データから判断できることは質問せず進める。

初期版は説明可能なルールベースを完成させる。高度なAI予測を先に作らない。

UIは「担当者が毎日迷わず使える」ことを優先し、最重要の指示（追加額／追加しない／停止継続）を最も目立たせる。
